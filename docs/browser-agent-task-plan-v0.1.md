## 1. 如何使用这份清单

每个子任务都有编号、前置依赖、交付物、验证动作和通过标准。完成实现后先执行该项验证，保存证据，再勾选。一个任务宜对应一个可独立审查的变更；任务较大时可继续拆成 `M1-12a` 等子项，但不能删除原任务的验收条件。

依赖表示“完成该任务的正式验收前，必须满足的前置条件”；接口确定后可提前用夹具开发，但夹具通过不能替代真实联调。阶段内不必严格按编号串行。人员、资源和模型尚未确定，不承诺固定日期；先完成 M0 和最小闭环，再依据实际耗时排期。七天监控本身需要七天连续观察窗口。

统一完成定义：交付物可定位；本项正向、边界和适用的故障验证通过；关联证据可重放或复核；残余问题明确；未改变原定权限、预算或验收门槛。需要真实网站验证的任务，如果只完成夹具验证，应保持未勾选并记录阻塞原因。

验证分为六类：**审查**（配置、契约、数据集）、**组件**（纯逻辑与边界）、**集成**（API/Worker/SQLite/浏览器联动）、**故障**（中断、竞态、损坏）、**真实闭环**（指定站点实际执行）、**正式评测**（冻结条件与独立判分）。这些结果分别保存，不能混为同一成功率。

建议每项记录：`状态 / 负责人 / 代码或文档版本 / 验证命令或人工步骤 / 实际结果 / 证据路径 / 遗留问题`。状态可使用 `TODO、IN_PROGRESS、BLOCKED、VERIFIED`；只有 `VERIFIED` 才勾选。正式评测另记 `PASS、FAIL、NOT_RUN`：评测执行及报告完成，不等于产品通过门槛。

| 阶段 | 子任务数 | 阶段交付与退出条件 |
|---|---:|---|

| M3 记忆、批次、接管与运行维护 | 18 | 可信流程、失效回退、批次隔离、接管排他、备份恢复均通过验证 |

| M4 冻结与正式验收 | 11 | 109 次正式任务、56 次监控及接管专项分别报告；如实给出是否达标 |
| **合计** | **85** | 子任务完成状态与产品最终验收结论分开记录 |

主路径是：最小契约 → 存储/状态/资源与预算 → 安全浏览器网关/证据/验证 → 只读闭环 → 四类闭环 → 记忆/批次/接管 → 冻结评测。写入意图及查证机制必须先于 GitHub 实际写入完成。

可并行的工作：M0 的来源、模型、测试仓库、基准资源调查；接口确定后的前端与后端；M1 后的各业务场景；WA 环境准备与 M1/M2；正式版本稳定后的七天监控与其他正式评测。WebArena 未就绪不阻塞公网开发，但整体验收必须保留其未完成项。

这些检查在各任务中已经安排；此表用于最终核对覆盖，不另增加任务数量。故障优先在可控夹具复现，真实网站验证只在既定低频与写入范围内进行。

## 10. 建议执行顺序与阶段检查点

1. **先完成准备和最小接口**：M0-01/02/08 优先；M0-03/05/06/07 可并行，任务集 M0-04 在来源及仓库/CI 准备就绪后完成。模型、测试仓库或基准尚缺配置时，先完成不依赖这些资源的组件工作。
2. **建立最小可验证闭环**：M1-01–M1-19 按依赖开发，界面 M1-20–22 并行接入；写入协议 M1-23 先在夹具验证；以 M1-24/25 作为进入真实业务扩展的门槛。
3. **并行建设业务和环境**：金融 M2-01–03、研究 M2-04–05、代码 M2-06–11、监控 M2-12–17 分支独立推进；WA-01 可更早开始。完成 M2-18 后已有可演示产品闭环。
4. **完善持续运行能力**：接管 M3-01–05、流程 M3-06–10、批次 M3-11–13 可并行；随后完成跨模块故障、数据运维和 M3-18。M4-01 报告工具可以提前开发。
5. **正式冻结后再计成绩**：M4-02/03 → 公开基础 M4-04 → 正式记忆 M4-05 → 配对 M4-06。七天监控 M4-09 和 WA 正式运行 M4-07/08 在各自依赖满足后并行，受全机两活跃槽和公开每日配额限制。公开 79 次正式任务即使无失败也不能挤在一个自然日完成；监控日常预留八次后，普通运行每日最多 42 次。
6. **按原始记录决定交付结论**：M4-11 汇总。开发功能完成、评测执行完成、产品达到门槛是三个不同结论；不因计划勾选较多就提前宣布项目验收通过。

框架验收随功能推进：M1 完成 FR-01–03 及已实现的暂停/预算部分；M2/M3 补齐 FR-04/05；M4 冻结前全部通过。FR-06–08 不进入首期关键路径，不能要求 browser-use 对比完成后才开始上述开发。
