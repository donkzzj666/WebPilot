# 基础机制集成故障验收

M1-24 在自有测试域中验证真实 API／Worker 提交故障及恢复。它不使用真实账号、付费模型、真实 GitHub 写入或保留评测答案；每次运行采用新目录，失败证据不能覆盖。

## 同一运行的故障对账

新增验收入口为 `scripts/verification/verify_fault_acceptance.py`。提交故障域从实际 API 启动任务，由 Worker、LangGraph 和受管浏览器执行自有页面读取，再在暂停提交、取消请求事务提交前／后停止进程。新进程恢复后核对同一 Run 的账本、业务事件、动作记录、证据工件、工作台和结果页。

恢复不得重置 budget ID、既有尝试、日额度或累计计数；旧执行器不能继续派发。202 是持久受理回执，完成须由新 Worker 在安全边界落库。重启后的同一幂等键不能产生第二个操作。成功域随后损坏自己的证据原件，历史聚合结论保留，当前 API／界面必须撤销完整成功展示。

既有恢复、写入、预算、控制、网关、证据和网络探针按固定子组复跑，提供故障广度。旧报告仅是历史参考，不能替代本轮执行结果。新增同域对账不将独立 UI 成功样例冒充崩溃恢复联动。

## 执行与证据

```sh
.venv/bin/python scripts/verification/verify_fault_acceptance.py \
  --output-dir <全新目录>
./scripts/check.sh --headed
.venv/bin/python scripts/verification/verify_clean_install.py
```

统一检查按顺序执行，首个失败即停止后续子组。跨层原件／诊断位于模式 0700 的 `.private/`，复跑子探针位于模式 0700 的 `.owned/`；内层探针按自己的输出边界导出安全工件。外层公开汇总及全新安装导出均排除这两个目录，最终私有哈希清单只提供路径和 SHA，不导出原件。子进程、浏览器和流必须退出后才做完整性与工件哈希检查。默认业务库、图库、私有凭据及旧验收文件不被迁移或重写。

本轮先修复 M1-22 历史写入授权投影：历史授权依据写入来源 Run 的冻结契约，当前 Run 能否复用另行核对；来源契约缺失或损坏为不可核查，不能凭所选新契约宣告旧写入违规。原失败报告保留。最终通过结果与失败历史见 [M1-24 验收记录](../m1/records/M1-24.md)。
