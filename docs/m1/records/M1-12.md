## 交付

- 全部本地 API，包括健康、查询和 SSE，统一校验私有 Bearer 令牌、精确 Host／Origin 和 Fetch Metadata。默认入口仅监听回环；无凭据为 401，越界来源为 403，跨域预检不授予权限。
- 384 位本机会话令牌保存在私有目录，不进入网页、URL、浏览器存储或普通日志。Vite 在来源和请求类型通过后服务端注入令牌；前端使用同源 `apiFetch`，正常 UI 无需手动粘贴令牌。
- 受管浏览器每上下文拥有独立认证代理；后台流量使用默认拒绝代理。公网拒绝私网和本机；WebArena 默认全部拒绝，只按可信配置开放协议／主机／业务端口；控制和管理端口优先拒绝。
- 出口验证每次 DNS 的全部答案，使用选定数字 IP 建连，并在转发前核对实际 socket 对端。HTTP 严格消息边界、代理凭据和 HTTPS CONNECT 目标限制避免请求混淆与连接绕过。
- 浏览器统一路由、本机文件保护、代理回环强制、QUIC 与 WebRTC 原生参数覆盖普通页面、iframe、弹窗、重定向、Worker 及实时通信；代理失效没有直连回退。
- 迁移旧 API 测试与使用示例为显式认证，更新前端、健康信息和验证入口，保持历史验收工件与快照原样。

配置、内部接口、支持范围和官方依据见[本地 API 与网络边界说明](../../development/network-security.md)。

## 故障定位与复核

首轮原生旁路实测发现，`force-webrtc-ip-handling-policy` 对有界面 Chrome 无效，UDP 探针收到 3 包。核对官方 Chrome 首选项映射，并进行 Chrome／headless-shell 对照后，确认二者使用不同的参数。生产启动现同时设置两个实际生效的参数；最终两种模式均为零越界连接，不再依赖 JavaScript 包装作为这条通道的安全边界。

验收脚本也修正了 `no-cors` 对代理 403 响应仍正常解析、Playwright 被阻止的注册返回空值、以及被阻断 iframe 没有可读执行环境而等待的问题。早期失败和诊断工件保留，最终结论依据上述完整检查和全新安装复验。源码和最终受测副本保持可核对；测试之后只补充文档与快照。

## 适用边界

本项验证的是锁定 Chromium 的受管浏览器出口与本机 API 防护，不是 OS 级零数据包声明或任意恶意本机代码沙箱。Service Worker 的常规注册被禁用，但真实出口检查才是其网络约束；不能把页面包装当成引擎完全禁用。

HTTP 代理限制请求体大小及消息格式，实时媒体、流式上传或某些 WebSocket 功能可能不可用，不自动放宽为直连。HTTPS 保持端到端证书验证；不拦截解密正文。真实 WebArena 尚未部署，本项使用显式登记的隔离业务夹具验证精确开放规则，不宣称真实基准已可运行。

任务执行仍关闭，登录身份确认、任务来源授权、动作与调度继续按后续 M1 子任务实施。已有旧 API／Worker 进程须重新启动才能载入新代码；本次验收未重启用户原有服务。
